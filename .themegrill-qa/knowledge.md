## ⚠ OPEN BUG — the Gutenberg block fatals every page it is on

**Severity: site-down for any page using the block. Found 2026-09-07, unfixed.**

`src/Frontend/Blocks/SurveyBlock.php:105` is a single physical line reading,
in effect:

```php
/** @var SurveyRepository $repo */ // phpcs:ignore … -- inline type hint		$repo = $this->container->get( SurveyRepository::class );
```

The `$repo = …` statement sits **after** a `//` line comment, so it never
executes. Line 106 then calls `$repo->findById()` on null:

```
Uncaught Error: Call to a member function findById() on null
  in src/Frontend/Blocks/SurveyBlock.php:106
```

**Observed, not inferred:**

- A published page containing `<!-- wp:allfeedback/survey {"surveyId":N} /-->`
  returns **HTTP 500** with WordPress's "critical error" page. The block never
  renders.
- It fires for **every** positive `surveyId` — published, draft, or dangling —
  because the fatal happens before the status check. Only `surveyId: 0` escapes,
  returning early.
- It also fires through the REST API, because `the_content` is rendered into post
  responses. Consequences: creating *or deleting* a page whose content contains
  the block answers 500, so such a page cannot be removed through the REST API
  at all until its content is blanked first.
- The shortcode path is unaffected, which isolates the fault to this renderer.

**Introduced by `37a1196`** — "fix: resolve PHPCS violations across entire plugin
to achieve zero errors and warnings" — which collapsed the docblock, the
`phpcs:ignore` comment and the statement onto one line. This is precisely the
fragility the fragile-areas section below flags: PHPCS was driven to zero twice
(`f0f9041`, `37a1196`).

**The fix is to put the assignment on its own line.** Nothing else is wrong with
the method.

Pinned in `tests/e2e/specs/building-forms/block-embed.spec.ts`: the three specs
asserting correct behaviour are marked `test.fail()`, so the suite stays green
while the bug stands and starts failing the moment it is fixed — at which point
delete the markers. A fourth spec proves `surveyId: 0` is safe, and a fifth
proves the shortcode still works.

## Architecture in one paragraph

A layered/DDD-ish plugin: a DI container (`src/Core/Container.php`) wires service
providers listed in `config/services.php`; domain entities and repository
interfaces live in `src/Domain/`, `$wpdb` implementations in
`src/Infrastructure/Database/Repositories/`; all admin UI is a **single React SPA**
mounted on one page, driven entirely by the `allfeedback/v1` REST API. There is no
server-rendered admin form anywhere — every admin assertion must go through the
SPA or the REST API, never through `$_POST` to `admin.php`.

Consequences for QA:

- Admin submenu items are **hash routes into one page** (`allfeedback#/forms`),
  not separate screens. Playwright must wait for SPA hydration, not `load`.
- The frontend widget is React too, injected by `src/Frontend/FrontendServiceProvider.php`.
- Nothing uses `wp_ajax_`; there are no admin-ajax endpoints to test.

**[verified] The three localized globals** — the only supported way in to the SPA:

| Global | Where | Carries |
|---|---|---|
| `window.__ALLFB_ADMIN__` | admin page (`AdminServiceProvider.php:304`) | `nonce` (wp_rest), `submitNonce`, `version`, `isAdmin`, `wizardStatus`, system info |
| `window.__ALLFB__` | frontend (`FrontendServiceProvider.php:288`) | `nonce`, `submitNonce`, widget settings |
| `window.__ALLFB_BLOCK__` | block editor (`SurveyBlock.php:79`) | `color` |

**[verified] The React mount point is `#ALLFB-Admin-Root`**
(`AdminServiceProvider.php:48`) — not a slug-derived id.

**[verified] There is no `data-testid` anywhere** in the admin SPA or the widget.
Specs must select by role, visible text, or the `allfb-*` BEM classes. Adding
test ids to the churn-heavy screens would be the single cheapest way to make
future specs less brittle.

**[verified] Hash-route redirects**: the bare page lands on `#/analytics`;
`#/settings` redirects to `#/settings/general`; `#/tools` to `#/tools/system-info`.

**[verified] Cookie auth alone is not enough.** Every admin route answers `401
rest_forbidden` unless the request carries an `X-WP-Nonce` header taken from
`__ALLFB_ADMIN__.nonce`. This is ordinary WordPress REST behaviour, but it looks
exactly like a permission bug from the outside — do not file it as one, and note
that it makes a *missing nonce* and a *missing capability* indistinguishable to
an anonymous prober.

**[verified] Every route wraps its payload** as `{"success":true,"data":{…}}`,
with the collection nested under a named key: `data.surveys`, `data.responses`,
`data.forms`, `data.logs`, `data.count`, `data.stats`, `data.status`.

**[verified] Two routes the source table above missed**:
`GET /responses/unread-count` (`ResponsesController.php:137`) and
`GET /analytics/forms` (per-form metrics incl. `session_metrics`).
`PUT /surveys/{id}` is the builder's autosave.

**Unauthenticated write paths.** Three routes take no capability check — but
`submit` is **not** open:

1. `POST /surveys/{id}/submit` — **[verified] requires a `nonce` parameter**
   checked against the `allfeedback_submit` action
   (`SubmitController.php:68,121`). Omitting it is `400
   rest_missing_callback_param`, not `401`. So the endpoint is anonymous but
   nonce-gated; an adversarial mission should target nonce *reuse* and lifetime
   rather than absence.
2. `POST /surveys/{id}/analytics/event` — anonymous session-event tracking.
   `TODO: confirm whether this is nonce-gated too.`
3. `/surveys/{id}/state` — any logged-in user, no capability check.

`SubmitController` guards it with a pipeline (`src/Application/Response/Pipes/`):
`ValidateSurveyIsActive` → `ValidateResponseData` → `ValidateConsentIfRequired`.
Draft surveys accept submissions **only** for an admin preview
(`SubmitController.php:144`), and user details are stripped for non-admins unless
`disable_user_details` is set (`SubmitController.php:164`).

`DevToolsController` (a fake-data generator, added in `f6cffb4`) registers nothing
unless `WP_DEBUG` is true (`DevToolsController.php:539`) — **verify that gate holds
on every release.** `LogsController` reads log files by id through `realpath()`
(`LogsController.php:362`); path traversal there is worth an adversarial mission.

## Persistence

**[verified] The status machine is `draft → published → trashed → gone`,
and deletion is deliberately two-step:**

| Call | Result |
|---|---|
| `POST /surveys` | always creates a **draft**, whatever status you pass |
| `POST /surveys/{id}/publish` | draft → published |
| `DELETE /surveys/{id}/trash` | → trashed; on an already-trashed survey **409** |
| `DELETE /surveys/{id}/delete` | permanent, **but 409 unless already trashed** (`SurveysController.php:565`) |
| `GET /surveys?status=all` | **400** `rest_invalid_param` — the enum is `draft`, `published`, `trashed` only |

The 409s are the contract, not a defect: a regression that let `/delete` remove a
live survey in one call would be silent data loss. Both are asserted in
`tests/e2e/specs/building-forms/survey-lifecycle.spec.ts`.

**Custom tables** (`database/migrations/0001_CreateInitialTables.php`), prefix + `af_`:

- `af_surveys` — `title`, `description`, `form_schema` longtext, `settings` longtext,
  `styling` json, `targeting` json, `status` (default `draft`), `conflict_reason`,
  `response_count`, `created_by`, timestamps.
- `af_survey_sessions` — `survey_id`, `session_id` (UNIQUE, varchar 36), `user_id`,
  `guest_id`, `status` (default `viewed`), `started_at` / `submitted_at` /
  `abandoned_at` / `last_active_at`.
- `af_responses` — `survey_id`, `response_data` longtext, `score` smallint,
  `page_url`, `device_type`, `ip_hash`, `ip_address`, `user_id`, `guest_token`,
  `consent_given`, `is_read`, `created_at`.

Note `af_responses` stores **both** `ip_hash` and `ip_address`. Whether the raw
address is meant to be retained when `disable_user_details` is on is a privacy
question — `TODO: confirm intended behaviour` before writing an assertion.

**Options** — only three of the plugin's own:

| Option | Purpose | Source |
|---|---|---|
| `_allfeedback_settings` | the entire settings tree | `src/Core/Settings/SettingsManager.php` |
| `_allfeedback_enabled_modules` | module toggles | `src/Modules/ModuleRegistry.php` |
| `allfeedback_wizard_status` | wizard completion / redirect gate | `src/Admin/AdminServiceProvider.php` |

No post meta, no CPTs, no taxonomies. `RoleManager::createRoles()` and
`removeRoles()` are **empty stubs** (`src/Core/RoleManager.php:33,43`) — the plugin
adds no custom roles, so the roles table below is short by design, not by omission.

**Settings defaults** (`SettingsManager.php:94-131`), the values a fresh-install
assertion should expect:

- `general.widget` — `color` `#6366F1`, `position` `bottom-right`, `trigger` `auto`,
  `delay` `0`, `scroll_threshold` `50`, `show_on_mobile` `true`
- `email.delivery` — `to_email` / `from_name` / `from_email` / `reply_to` all `''`
- `email.notifications` — `admin_enabled` `true`, `respondent_enabled` `true`
- `advanced.privacy` — `disable_user_details` `false`, `require_consent` `false`,
  `consent_text` "I agree to the storage and handling of my data.",
  `privacy_policy_url` `''`
- `advanced.logging` — `enabled` `false`, `level` `debug`, `retention_days` `30`
- `advanced.plugin` — `delete_on_uninstall` `false`

**Enums** (`SettingsManager.php:144-154`) — anything outside these should be rejected:
`position` ∈ {`bottom-right`, `bottom-left`, `side-tab`}; `trigger` ∈ {`auto`,
`scroll`, `exit-intent`, `manual`}; logging `level` ∈ {`error`, `warning`, `info`, `debug`}.

## Frontend surfaces

- **Shortcode** `[allfeedback_survey]` — `src/Frontend/FrontendServiceProvider.php:131`
- **Block** `AllFeedback Survey` — `src/Frontend/Blocks/SurveyBlock.php`, registered
  through `AbstractBlock::register()` (`AbstractBlock.php:90`). Renders a static
  preview via `surveyPreviewHtml()` in `resources/scripts/shared/formPreview.ts`;
  there is no PHP form rendering.
- **Floating widget** — chosen by `TargetingEngine` (`src/Frontend/TargetingEngine.php`).
  `resolveForCurrentPage()` picks one survey; rules are matched in `evaluateRule()`
  (line 234) over types `page_id`, `post_id`, `post_type`, filterable through
  `allfeedback_targeting_rule_matches`. `matchesSettingsTargeting()` (line 177)
  reads `targetPages` / `target_pages` ∈ {`all`, `specific_pages`/`specific`,
  `specific_posts`} plus `target_page_ids`.

Only published surveys render on the frontend (`SurveyBlock.php:91`,
`SurveysController.php:327`). **[verified]** on a live site: a draft survey
produces no `.allfb-widget` at all, and its shortcode is consumed without
rendering a form — though `frontend.css` and `frontend.js` are still enqueued on
a page whose shortcode points at a draft, which is harmless but wasteful.

**[verified] Widget DOM** — the selectors any frontend spec needs:

```
.allfb-widget[data-position]      wrapper; gains .is-revealed once mounted
  .allfb-launcher                 the button; gains .is-open while the panel is open
  #allfb-panel.allfb-panel        the panel; .is-open + aria-hidden="false" when open
    .allfb-panel__title / __close
```

**[verified] The trap worth knowing: the default trigger is `auto`, so the panel
opens itself on load.** A spec (or a manual tester) that clicks the launcher to
"open" it actually *closes* it, and the next click lands on whatever theme
content sits underneath. Check for `.allfb-panel.is-open` before clicking — see
`tests/e2e/support/widget.ts`. This cost three failing specs on the first run.

## Roles and capability boundaries

The plugin defines no roles of its own. Everything admin-facing is `manage_options`,
i.e. Administrator only (single site).

| Actor | Expected |
|---|---|
| Administrator | full access to all seven admin routes and every admin REST route |
| Editor / Author / Contributor / Subscriber | no admin UI; every `adminPermission()` route → 403 |
| Logged-in, any role | `/surveys/{id}/state` succeeds (`is_user_logged_in`) |
| Anonymous | `/surveys/{id}/submit` and `/analytics/event` succeed on a **published** survey; everything else 401/403 |
| Anonymous, draft survey | submit must be rejected (`ValidateSurveyIsActive`) |

**[verified]** Every route in the admin list answers `401 rest_forbidden` to an
anonymous caller, including `content-search`, `logs` and `about/video`, and
anonymous `POST /surveys` and `PUT /settings` are refused. Asserted in
`tests/e2e/specs/permissions/rest-permissions.spec.ts`.

**[verified — earlier claim corrected] The `/dev-tools/*` gate could NOT be
verified here, because this install has `WP_DEBUG = true`.** The routes *are*
registered on it — the namespace index lists `/dev-tools/seed` (POST, DELETE),
`/reset-wizard` (POST), `/reset-settings` (POST) and `/logs` (DELETE). An earlier
draft of this file read a `404` as proof the gate held; that `404` was really a
method mismatch, since WordPress answers `404 rest_no_route` for a GET on a
POST-only route. What the suite asserts instead is the thing that holds either
way: these destructive routes refuse an anonymous caller (401 when registered,
404 when not — never 200). Verifying the `WP_DEBUG`-off behaviour needs a
production-like site.

## Expected behaviour — lifted from the docs

Each line below is the product owner's own phrasing and is a ready-made assertion.
`TODO: verify each against 1.0.0` — an unverified doc line is a candidate finding,
not a fact.

**Displaying forms** (<https://docs.allfeedback.net/building-forms/displaying-forms>)

- The first matching form the visitor is eligible to see is displayed as a floating widget.
- If no form matches, no widget appears.
- **Exclusion rules always win.** If a page matches both an inclusion and an exclusion rule, the form will not appear.
- If a form is set to *Specific Pages or Posts* but no pages or posts are selected, the widget will never appear.
- **Only one widget is shown per page.** If several forms match, the most recently published form the visitor is still eligible to see is displayed — after audience (logged-in/logged-out) and frequency limits.
- Draft forms will not appear even if the shortcode is present.
- If the form is set to *Draft*, the block renders nothing.
- If a page has both an embedded form and a matching targeted widget, **both** appear — the embedded form inline and the widget floating.
- Drafts and private posts do not appear in content-search results.

**Settings** (<https://docs.allfeedback.net/settings/>)

- The consent checkbox appears automatically on all surveys when `require_consent` is on.
- The *To email* address receives new-response notifications and the weekly digest.
- The position control includes a browser mockup previewing the widget's placement.
- Trigger Icon is shown only when position is Bottom right or Bottom left; Side tab uses a text label.

**Analytics** (<https://docs.allfeedback.net/analytics-reporting/>)

- The NPS distribution card appears **only** for surveys containing an NPS-type question.
- The Session breakdown card appears only when a single survey is selected.

**Getting started** (<https://docs.allfeedback.net/getting-started/installation-and-setup>)

- After activation the user is redirected to the Setup Wizard.
- The wizard keeps appearing until it has been completed.

Every spec creates its own fixtures and destroys them, so the suite is
re-runnable and leaves the install as it found it (checked after two runs: one
draft survey, zero responses, no stray pages or users, settings restored). It
runs `workers: 1` because it mutates one shared WordPress.

**Two hard-won details, both encoded in `support/`:**

- **Role boundaries need application-password auth.** A 401 from an anonymous
  caller proves nothing on its own, because a missing nonce produces the same
  status as a missing capability. `Wp.createRoleUser()` therefore mints a
  WordPress application password per fixture user and calls the API with HTTP
  Basic auth, which carries real capabilities and needs no nonce. It skips
  cleanly if application passwords are unavailable (they need HTTPS or a
  `local`/`development` environment type) rather than reporting a false pass.
- **Widget interaction must not happen on the site home page.** The active
  theme's hero image overlays the fixed-position widget and intercepts the
  click, which made three specs flaky rather than honestly failing. Every
  interaction spec now runs on a blank page created for it
  (`Wp.createBlankPage`). Whether that overlap is also a real z-index defect in
  the widget is `TODO: worth a maintainer's eye` — the suite routes around it
  rather than judging it.

**`area_paths` in `suite.json` is a proposal, not a decision.** Six areas, all
globs mechanically validated to match real files, mapping 132 of 243 source
files (54%). The unmapped remainder is cross-cutting **on purpose** — `config/`
(DI wiring), `src/Core/{Container,Events,Jobs,Cache,Features,Exceptions}`,
`src/Support/` except `Logger`, `src/Modules/`, `src/Traits/` and the shared
admin components affect every area, so a change to them correctly falls back to
the full tier. Narrowing those would trade coverage for speed. A maintainer
should still ratify the six per-domain lists.

Gaps that remain, and why:

- **Migrations and uninstall** — `wp allfeedback migrate reset/refresh` and the
  `delete_on_uninstall` branch destroy data, so they need a disposable site
  (`run-suite.mjs --boot`), not this one. There is no REST surface for
  migrations; the CLI is the only entry point.
- **Email** — `settings/test-email` and the three notifications need a mail
  catcher. Asserting them here would send real mail.
- **The drag-and-drop form builder UI** — still untested, and still the
  churn-heaviest code in the product (`AllForms.tsx` 50 modifications,
  `PreviewPanel.tsx` and `FormBuilder.tsx` 48 each). The API beneath it is
  covered; the interaction is not. This is the largest remaining risk.
- **`WP_DEBUG`-off behaviour** — see the dev-tools note above.
